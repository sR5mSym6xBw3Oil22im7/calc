2. 目的

GitHub Pages上の静的Webアプリケーションを継続利用するための確認、障害対応、変更、復旧および管理手順を定義する。

3. 適用範囲

テスト利用組織が利用する公開ページと、リポジトリcalcのソース管理を対象とする。

5.3 障害重要度

障害重要度
重要度基準対応方針
重大電卓を利用できない、または計算結果が誤る最優先で対応
高主要機能の一部を利用できない早急に対応
中一部の表示または演出に問題がある計画的に対応
低軽微な表示差異または改善要望次回改修で検討

5.4 障害受付・初動・切り分け

  1. 発生日時、URL、ブラウザ、操作手順、期待結果、実際の結果、画面またはConsole情報を記録する。
  2. 重大度を判定し、テスト保守担当者が対応を開始する。
  3. 公開ファイル取得、JavaScriptエラー、外部フォント、ブラウザ差異、キャッシュを切り分ける。
  4. 計算誤りの場合はcalculate、normalizeResult、状態変数、再現入力を優先確認する。
  5. 演出問題の場合はCanvas寸法、配列上限、requestAnimationFrame、visibilitychangeを確認する。

5.5 復旧・エスカレーション

  1. 軽微なキャッシュ問題はハードリロードで確認する。
  2. 公開ファイル破損や回帰不具合は、正常コミットへロールバックしてmainへpushする。
  3. 復旧後に初期表示、主要計算、エラー復帰、レスポンシブを確認する。
  4. 計算誤りまたは長時間復旧しない場合はテスト承認者へエスカレーションする。
  5. 原因、対応、再発防止を障害記録へ残す。

5.6 変更・回帰テスト

  • 変更要求を受け付け、要件ID・設計ID・実装関数・テストIDへの影響を調査する。
  • mainへ直接未確認変更を反映せず、差分レビューと回帰テストを実施する。
  • 変更内容に応じて07_テスト計画・テスト仕様書の関連ケースを再実施する。
  • リリースは09_リリース手順書に従う。

5.7 バックアップ・バージョン管理

  • Gitコミット履歴をソースのバックアップとし、公開前コミットを記録する。
  • バージョン、公開日、変更概要、確認結果をリリースノートへ記録する。
  • 一時ファイル、バックアップファイル、展開途中フォルダをリポジトリへ含めない。

FAQ

5.10 保守終了時の対応

  • 最終版ソース、文書、リリース履歴、既知問題を保管する。
  • 公開停止が必要な場合は利用組織と承認者の合意後にGitHub Pages設定を変更する。
  • 公開URLの案内と終了日を関係者へ通知する。

6. 前提条件・制約事項

使用しない構成

本システムに独自のサーバー監視、バックエンド、データベース監視は存在しないため、必須運用作業としない。

7. 補足事項

補足事項

対応期限は確定値として「随時対応」である。個別障害の目標復旧時間は別途合意が必要である。
